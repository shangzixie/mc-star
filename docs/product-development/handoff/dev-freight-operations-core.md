# Development Handoff Spec - Freight Operations Core

## Goal

把发货管理主链路落成一个内部运营后台，先保证数据正确和操作清晰，再逐步补强细节能力。

## Scope

- 适用角色：业务、客服、仓库、管理
- 所属阶段：MVP 核心链路
- 相关能力：入库、库存、货物改包、发货单、柜、出货、附件

## Delivery Surface

- 页面：内部管理后台 freight 相关页面
- API：`/api/freight/**`
- 数据：`src/db/schema.ts` 对应 freight 相关表
- 业务写入：通过 freight 领域服务集中表达，避免同一业务动作散落在多个入口

## Preconditions / State Requirements

- 主数据先存在：合作方、运输节点、仓库
- 入库后才能形成库存批次
- 出货必须基于库存批次
- 最终扣库存只能发生在明确出库动作
- 货物改包必须基于现有可用库存，并生成新的承接库存

## Input

必填：
- 业务单号 / 入库单号等业务标识
- 对应主数据主键
- 数量字段

可选：
- 联系资料
- MBL 信息
- 员工分配
- 附件
- 快递信息（快递单号、收货时间）
- 空运扩展（航空类型）

## Validation Rules

1. 数量相关校验必须放在后端
2. 出货状态必须单向推进
3. 任何库存扣减都必须可回溯到流水或分配记录
4. 前端不得绕过后端约束自行认定库存可用量
5. 新建 `warehouse_receipts` 时，默认状态必须为 `INBOUND`
6. 出库 `SHIPPED` 后必须回写并重算所属入库单状态，避免库存与单据状态漂移
7. 入库单号在单据未进入 `OUTBOUND` 前允许修正；进入 `OUTBOUND` 后按锁定规则禁止修改
8. 集拼合并创建只能生成海运拼箱单据；普通入库创建入口不应提供海运拼箱选项
9. 运输类型、状态推进、库存扣减等关键规则必须在服务端校验，不能只依赖前端选项限制
10. 货物改包创建成功后，旧入库单库存必须扣为 0 并进入 `OUTBOUND`，新入库单逐条复制旧单可用库存明细作为新库存
11. 货物改包是创建动作模式，不是运输类型；新改包单创建时不要求 `transportType`
12. 货物改包新单的明细在详情页作为当前单库存明细编辑；旧入库单只作为来源引用，不因新单编辑而联动变更
13. 总列表导出 Excel 只能基于现有 `INBOUND` 库存单据选择；导出是只读动作，不改变库存、状态或流水

## UX Notes

1. 非技术人员优先，避免复杂多层弹窗和隐藏入口
2. 创建流程优先最小必填，再在详情页补录
3. 列表页应优先提供搜索、状态筛选、查看详情
4. 详情页应按业务区块拆分，而不是一次展示全部字段
5. 入库详情返回行为优先遵循浏览器返回栈，兜底回到入库列表
6. 联系资料区块需支持客户/发货人/订舱代理/清关代理电话编辑与展示
7. 业务员从“内部资料”区块迁移到“联系资料”区块，位于发货人下方
8. 快递信息应并入入库详情的船期区块，显示在库房名称下方，不再保留独立快递信息卡片
9. 单套提单区块可编辑入仓时间
10. HBL 移除“收货地”，MBL 移除“目的港地址”和“收货地”前端录入入口
11. 入库详情页应保持稳定的信息编排：基础信息、船期与入库明细关系清晰；快递信息作为船期区块内部补充信息呈现，不依赖临时拼接布局
12. 入库明细列表在详情页头部区域应占满右侧剩余宽度并贴齐最右边，不保留无意义留白列
13. 入库单号编辑应复用既有低学习成本模式，不新增独立复杂流程
14. 集拼场景下，业务员不需要手动判断运输类型，入口语义应直接表达“合并创建”
15. 货物改包场景下，业务员应先选择旧入库单，再输入新入库单号完成创建；页面需要明确提示旧单会转为出库状态
16. 货物改包创建后的新单详情页应让业务员直接修改新单明细；旧单入口用于追溯来源，不应造成“正在编辑旧单明细”的误解
17. 总列表的 Excel 导出入口应先进入“选择现有库存”模式，再由业务员勾选单据并下载结果，避免隐藏式批量操作

## Acceptance

1. 用户可以完成入库、查看库存、推进出货
2. 库存数量变化可追踪
3. 页面交互不要求技术背景即可理解
4. 新功能进入实现前，能在 `coding/` 找到对应技术事实
5. 货物改包后，新旧入库单的库存变化可通过库存流水追溯
